## 2. 为什么要"重构"

经过前三课，`tensor.rs` 已经长成了一个功能完整的张量库：构造、形状、逐元素运算、广播、归约、softmax、matmul、自动微分……如果所有代码继续堆在一个文件里，很快就会失控：

- **职责不分**：张量运算、自动微分、模型层、训练逻辑混在一起，改一处可能碰坏另一处
- **无法复用**：后续每节课都要加新东西（层、损失、优化器、Transformer 模型），没有清晰的模块边界就没法增量开发
- **依赖混乱**：谁依赖谁说不清，改个接口要满项目搜索

所以这一课做两件事：

1. **横向**：把项目按职责拆成多个 `.rs` 文件，形成清晰的依赖金字塔
2. **纵向**：深入理解 `Tensor` 的 `Arc<Mutex>`/Shared 架构——它是一切上层建筑的地基，前三课里所有算子都建立在这套设计之上

## 4. 核心架构：Shared<Vec<f32>>（Arc<Mutex>）跨线程共享可变数据

先看 `Tensor` 的结构体（`src/tensor.rs`）：

```rust
#[derive(Clone)]
pub struct Tensor {
    data: Shared<Buffer>,        // 数值（前向结果）
    shape: Vec<usize>,           // 形状
    strides: Vec<usize>,         // 视图步长（第 5 课）
    grad: Shared<Vec<f32>>,      // 梯度（反向累加）
    requires_grad: Arc<AtomicBool>, // 是否需要梯度（参数=true，数据=false；Relaxed 原子读写）
    // 计算图结构不在张量上：反向闭包统一登记到 autograd 的线性 tape
}
```

两个问题：**为什么数值和梯度要共享？共享之后怎么才能"可变"？**

### 4.1 Arc：多个句柄指向同一份数据

计算图里一个节点经常被**多个运算同时引用**。比如 `z = x·y + w` 里 `y` 只被用一次，但看下面这种图：

```
          x ──┐
               mul ──► t ──┐
          x ──┘            add ──► z      （x 被用了两次！）
          w ───────────────┘
```

`x` 同时是两次运算的输入。如果 `Tensor` 直接 `pub data: Vec<f32>`，克隆一个 `Tensor` 就要**复制整份数据**；而 `Arc<T>`（原子引用计数）允许无数个 `Tensor` 句柄共享同一个底层数据，克隆只把引用计数 +1（原子操作），是 **O(1)** 的操作。这也是 `#[derive(Clone)]` 能放心用的前提。

### 4.2 Shared（Arc<Mutex>）：跨线程的共享可变数据

`Arc` 只解决"共享"，不解决"可变"——`Arc<T>` 的内容默认不可变。但我们的张量既被多处引用、又需要更新（前向写 `data`、反向写 `grad`）。Rust 的常规借用规则（一个值同时只能有一个可变借用）会拒绝这种写法。

`Mutex<T>`（互斥锁）把借用检查从**编译期**推迟到**运行期**：`borrow()` 只读借用、`borrow_mut()` 可变借用，内部都是加锁拿到 `MutexGuard`，同一时刻只能有一把锁，锁被持有时再借会阻塞等待。`tensor.rs` 顶部用薄封装 `Shared<T>(Arc<Mutex<T>>)` 暴露它（内部用 `PoisonError::into_inner` 忽略锁毒化），调用写法与旧方案完全一致。这就是"跨线程共享可变数据"的标准解法：

| 组合 | 解决的问题 | 代价 |
|------|------------|------|
| `Arc<T>` | 多个句柄跨线程共享一份数据 | 只读共享 |
| `Mutex<T>` | 共享的数据还能改 | 加锁开销、锁未释放时阻塞 |
| `Arc<Mutex<T>>`（即 `Shared<T>`） | **跨线程共享 + 可变** | Mutex 不可重入，需要锁纪律 |

对应到代码里的经典模式：

```rust
let sd = self.data.borrow();          // 读：前向计算
// …… 用完立刻释放，避免同一把锁重叠
drop(sd);
let mut g = self.grad.borrow_mut();   // 写：反向累加梯度
```

**注意代码里几乎每个算子的前向都有 `drop(sd); drop(od);`**——因为之后构造结果节点要 `borrow_mut` 自己的东西。`Mutex` 不可重入：同一把锁还没释放就再借一次会**死锁挂起**。这是加锁使用者的纪律。另外，同一底层缓冲可能被借两次的位点（`x*x` 自乘、matmul 传入同一个张量）必须先 `Shared::ptr_eq` 判同一、只借一把锁，第二个视图用 `Option<MutexGuard>` 接住。

### 4.3 为什么 data 和 grad 分开两个 Shared

细看：`data` 和 `grad` 是**两个独立**的 `Shared<Vec<f32>>`。除了"语义上一个是数值、一个是梯度"之外，还有两个实际好处：

1. **可以同时读 data、写 grad**：反向闭包里常见 `let sd_b = sd.borrow(); let mut sgm = sg.borrow_mut();`——两者是两把不同的锁，互不冲突。
2. **grad 的指针充当计算图节点 ID**：`backward` 里用 `Shared::as_ptr(&t.grad) as usize` 唯一标识一个节点（见第 6 节）。注意不能用 `data` 指针判重——`reshape` 等视图运算与输入共享 `data`，会误把父节点跳过导致梯度截断。`grad` 的指针还用来判断"两个父节点是不是同一个张量"（`Shared::ptr_eq(&sg, &og)`，处理 `x*x` 自乘的梯度合并）。

### 4.4 为什么是 Arc<Mutex> 而不是 Rc + RefCell

早期版本确实用过 `Rc` + `RefCell`（单线程、无锁，更轻）。但 `Rc`/`RefCell` 都不是 `Send`/`Sync`，会把计算图和整个模型锁死在单线程里，堵死 rayon 数据并行——而张量是全库最底层的类型，它不满足 `Send`，上层一切都无法跨线程。因此全库换成了 `Arc<Mutex>`（经 `Shared<T>` 薄封装）：张量可跨线程共享，为数据并行打开大门；加锁开销相对并行收益可以忽略；`Shared::borrow()`/`borrow_mut()` 保持原来的调用写法，数值语义逐位不变，checkpoint 格式也不受影响。

## 5. 计算图为什么住在全局线性 tape 里

早期版本把图结构挂在张量上：`parents: Arc<Vec<Tensor>>` + `backward: Option<BackwardFn>` 每节点各存一份。它留下了两个教训，正是现在改成线性 tape 的原因。

### 5.1 教训一：绝不能存 `parents: Vec<Tensor>`

最早的版本 `parents` 直接存 `Vec<Tensor>`。每个运算在构造结果时都要记录父节点：

```rust
result.parents = vec![self.clone(), other.clone()];   // 每个算子都这么干
```

问题出在 `self.clone()`。如果 `parents` 的类型是 `Vec<Tensor>`，那么 `clone` 一个 `Tensor` 时：

- `data`：`Shared`/`Arc` 共享 → O(1)
- `shape`：`Vec<usize>` → O(维度数)
- `grad`：`Shared`/`Arc` 共享 → O(1)
- **`parents`：`Vec<Tensor>` → 递归克隆所有父节点！**

而父节点自己又有 `parents`……于是 `clone` 会**递归复制整棵祖先子树**。设计算图深度为 L：

| 方案 | 建一个新节点的开销 | 一次前向（L 个节点） | N 步训练 |
|------|--------------------|----------------------|----------|
| `parents: Vec<Tensor>` | O(L)（递归深拷贝） | O(L²) | **O(N·L²)** |
| `parents: Arc<Vec<Tensor>>` | O(1)（Arc 引用计数 +1） | O(L) | O(N·L) |

线性回归的计算图只有几层，L 很小，第 2 课那样写还能跑；但到了 Transformer（几十层 Transformer），每步前向要建几百上千个节点，`O(L²)` 的复制会直接拖垮训练——这就是"性能灾难"。这也是 4.4 节 `Rc`→`Arc` 改造的一部分：**节点句柄必须共享，绝不能深拷贝**。

### 5.2 教训二：每节点一份 `parents + backward` 本身也是开销与负担

即便用 `Arc<Vec<Tensor>>` 解决了深拷贝，每个节点仍要各挂一条父指针链和一个 `Option<BackwardFn>`：

- **建图期**：每个算子要为结果组装 `parents`（Vec 分配 + Arc 装箱），克隆张量还要连带克隆这些字段；
- **反向期**：要从 loss 出发 DFS 遍历这张指针图、三色标记去重、产出拓扑序再逆序执行——一套完整的图遍历算法，深层图上还有栈溢出风险（6.2 节历史上的"迭代式 DFS"补丁就是为此打的）。

现代框架（PyTorch 的 autograd.engine 等）用**线性 tape**：反向闭包按前向发生顺序登记进一张全局表，反向时**逆序扫描**即可——子节点总比父节点登记得晚，逆序天然就是拓扑逆序，一趟扫描搞定，不需要图遍历：

```rust
// autograd.rs：登记（前向时每个算子调一次）
pub fn record(out: &Tensor, parents: Vec<Tensor>, f: BackwardFn);

// 反向时从 tape 末尾逆序扫，沿身份键可达的条目才执行
for i in (0..tape.len()).rev() { /* 执行闭包，父键入可达集 */ }
tape.retain(|e| !e.done);   // 只移除本次执行的条目
```

`Tensor` 于是瘦身成纯数据本体（数据/形状/步长/梯度/开关），计算图住在 `autograd.rs` 的 `static TAPE` 里。条目里的 `parents` 只是 `usize` 身份键（grad 缓冲地址），比存 `Vec<Tensor>` 句柄更轻，回溯时不持有任何张量锁。

> 历史备注：5.1 节的"深拷贝灾难"在今天以另一种形式被守住——`record` 的 `parents: Vec<Tensor>` 是一次性短命参数，登记完即丢；闭包捕获的 `Tensor` 全是 `Shared` 句柄的 O(1) clone。

## 6. backward：逆序扫描线性 tape

### 6.1 为什么逆序就是拓扑序

反向传播要求梯度**从输出端向输入端逐层传递**：`z = (x·y) + w` 里，必须先执行 `z` 的 backward（把梯度分给 `t`、`w`），`t` 的梯度就绪后才能执行 `t` 的 backward（再分给 `x`、`y`）。

线性 tape 按**前向发生顺序**追加：算 `t = x·y` 时 `t` 先登记，随后算 `z = t + w` 时 `z` 才登记——**子节点总是比父节点登记得晚**。于是从 tape 末尾向前逆序扫描，天然就是"先子后父"的合法反向执行序，不需要显式跑拓扑排序。

### 6.2 代码：逆序单趟扫描 + 可达集裁剪

> 见 `src/autograd.rs`。

```rust
pub fn backward(&self) {
    assert_eq!(self.rank(), 0, "backward() 只支持标量（0 维）输出，当前形状 {:?}", self.shape);
    {
        let mut g = self.grad.borrow_mut();
        g[0] = 1.0;                     // ① loss 的梯度 = 1（∂loss/∂loss = 1）
    }

    let root = Shared::as_ptr(&self.grad);   // 用 grad 地址作根身份键
    let mut tape = TAPE.lock()...;           // ② 锁住全局 tape
    let mut reachable: HashSet<usize> = HashSet::new();
    reachable.insert(root);

    for i in (0..tape.len()).rev() {         // ③ 从末尾逆序扫描（逆序 == 拓扑逆序）
        if reachable.contains(&tape[i].out) {
            (tape[i].f)();                   //    执行链式法则闭包
            reachable.extend(&tape[i].parents);  // 父键入可达集，继续向上游回溯
            tape[i].done = true;
        }
    }
    tape.retain(|e| !e.done);                // ④ 只移除本次执行的条目
}
```

三个关键设计：

| 设计 | 原因 |
|------|------|
| `Shared::as_ptr(&t.grad)` 做身份键 | `Tensor` 没有自增 id；用梯度 `grad` 的堆地址当身份证最省事，同一张量的所有句柄地址相同（不加锁，直接取内部指针） |
| 可达集裁剪 | 一个节点可能被多条路径回溯到（如 `x` 被用两次），闭包**只能执行一次**否则重复累加；可达集同时保证只反与 loss 相关的子图——流水线多 micro-batch 前向交错时，其它图的条目原样保留，等它们自己的 backward |
| 逆序 == 拓扑逆序 | tape 按前向顺序追加，子节点总是登记得晚；从尾往前扫一遍就是"根 → 叶"的梯度流向，不需要显式图遍历 |

### 6.3 走一遍例子：z = (x·y) + w

```
        x ──┐
             mul ──► t ──┐
        y ──┘            add ──► z
        w ───────────────┘
```

本例 tape（按前向顺序）：`[mul(t=x·y), add(z=t+w)]`。逆序扫描（`z → t`）：

| 顺序 | 条目 | 执行的闭包 | 效果 |
|------|------|-----------------|------|
| 1 | add | （收到的 g = 1） | t += 1，w += 1 |
| 2 | mul | （收到的 g = 1） | x += 1·y = 3，y += 1·x = 2 |

叶子 x/y/w 的键回溯不到任何条目，扫描自然结束——它们的梯度已在上面两个闭包里被写入。

和 `test_chain_rule` 验证的结果一致：`∂z/∂x = y = 3`、`∂z/∂y = x = 2`、`∂z/∂w = 1` ✓

## 7. module.rs：Module trait 与 zero_grad_all

### 7.1 trait 定义

深度学习里一切"可训练的结构"（Linear、LayerNorm、Transformer Block、整个 Transformer……）都需要回答一个问题：**你有多少参数？** `module.rs` 就把这个回答统一成接口：

```rust
// src/module.rs（全文）
use crate::tensor::Tensor;

/// 模块接口：任何可训练结构都实现它
pub trait Module {
    /// 返回模块的所有参数（含嵌套子模块）
    fn parameters(&self) -> Vec<Tensor>;
}

/// 便捷方法：清零所有参数的梯度
pub fn zero_grad_all(module: &dyn Module) {
    for p in module.parameters() {
        p.zero_grad();
    }
}
```

`Module` 目前只要求实现一个方法 `parameters()`。别小看这一个方法——**它是优化器、训练循环、梯度清零与模型结构之间的唯一桥梁**。

### 7.2 三个实现者：叶子模块

`layers.rs` 里三个最简单的实现：

```rust
// Linear：线性层 y = xW + b
impl Module for Linear {
    fn parameters(&self) -> Vec<Tensor> {
        vec![self.weight.clone(), self.bias.clone()]
    }
}

// LayerNorm：层归一化
impl Module for LayerNorm {
    fn parameters(&self) -> Vec<Tensor> {
        vec![self.gamma.clone(), self.beta.clone()]
    }
}

// Embedding：词嵌入查表
impl Module for Embedding {
    fn parameters(&self) -> Vec<Tensor> {
        vec![self.table.clone()]
    }
}
```

注意 `clone()` 在这里是安全的：因为 `Tensor` 内部全是 `Arc`/`Shared` 句柄（第 4、5 节），克隆只复制句柄，**不复制数据**——返回 `Vec<Tensor>` 给外部持有也不会有性能问题。

### 7.3 组合模式：大模块递归收集小模块的参数

`model.rs` 里的 `Transformer` 由若干 `TransformerBlock` 组成，`TransformerBlock` 又由 `LayerNorm`、`MultiHeadAttention`、`Linear` 组成。每个组合模块实现 `Module` 时，把**子模块的参数拼接起来**：

```rust
// model.rs：Transformer
impl Module for Transformer {
    fn parameters(&self) -> Vec<Tensor> {
        let mut ps = self.tok_emb.parameters();      // 词嵌入
        for block in &self.blocks {
            ps.extend(block.parameters());           // 每层 Transformer Block
        }
        ps.extend(self.ln_f.parameters());           // 最终 LayerNorm
        // 输出头没有独立参数：forward 里用 tok_emb.table.transpose() 做权重绑定
        ps
    }
}
```

因为 `parameters()` 是 trait 方法，`block.parameters()` 会自动递归调用 `TransformerBlock` 的实现，后者又调用 `MultiHeadAttention` 的实现……最终**一棵参数树被拍平成一张参数表**。

```
Transformer.parameters()
├── tok_emb.parameters()        → [table]
├── block[0].parameters()       → ln1[γ,β] + attn[c_q,c_k,c_v,c_proj] + ln2[γ,β] + mlp[W1,b1,W2,b2]
├── block[1].parameters()       → …
└── ln_f.parameters()           → [γ, β]
    （lm_head 通过权重绑定复用 tok_emb.table.T，不单独存储）
```

### 7.4 与优化器的配合（main.rs 的 demo_xor）

`main.rs` 里第 7 课的 XOR 演示展示了完整闭环：

```rust
// ① 收集所有参数，一次性交给优化器
let params: Vec<Tensor> = {
    let mut ps = fc1.parameters();
    ps.extend(fc2.parameters());
    ps
};
let mut opt = SGD::new(0.5, params);

// ② 训练循环：前向 → 反向 → 更新 → 清梯度
for step in 0..1000 {
    let h = tanh(&fc1.forward(&x_data));
    let logits = fc2.forward(&h);
    let loss = cross_entropy_loss(&logits, &y_targets);
    loss.backward();     // 自动算所有参数的梯度
    opt.step();          // SGD 遍历 params 更新：θ -= lr·g
    opt.zero_grad();     // 清零，防累加
}
```

分工很清晰：

| 角色 | 谁 | 干什么 |
|------|-----|--------|
| 参数清单 | `Module::parameters()` | 告诉外界"我的参数在哪" |
| 梯度计算 | `Tensor::backward()` | 自动微分填满每个参数的 `grad` |
| 参数更新 | `optim.rs` 的 `SGD` / `AdamW` | 按梯度更新 `data` |
| 梯度清零 | `Tensor::zero_grad()` / `zero_grad_all()` | 重置 `grad` 为 0 |

`zero_grad_all` 就是"把清梯度也统一成接口"：传入任意 `&dyn Module`，它调用 `parameters()` 拿到所有参数逐个清零。实际训练中优化器（如上面 `SGD::zero_grad`）自带同样的清零逻辑，而 `zero_grad_all` 的价值在于：**不经过优化器也能直接清任意模块的梯度**（比如想"只求梯度、手动更新"时）。任何新模块只要实现 `Module`，就能复用这套参数管理设施。

## 10. 本课总结

- 项目按职责拆成 19 个 `.rs` 文件（`tensor` / `autograd` / `rope` / `attention` / `gpu` / `module` / `layers` / `loss` / `optim` / `rng` / `data` / `tokenizer` / `model` / `train` / `sample` / `config` / `checkpoint` / `cli` / `main`），依赖呈金字塔形，`tensor.rs` 是最底层地基
- `Shared<Vec<f32>>` = 共享（Arc）+ 可变（Mutex），是跨线程"共享可变数据"的标准方案
- `parents`/`backward` 不再挂在张量上：反向闭包经 `record` 登记进全局线性 tape，条目只存 grad 地址身份键，`Tensor` 瘦身成纯数据本体
- `backward` 逆序单趟扫描 tape（逆序 == 拓扑逆序）+ 可达集裁剪，保证梯度按依赖序从 loss 流回叶子
- `Module` trait 统一"收集参数"，配合 `zero_grad_all`、优化器、训练循环形成完整闭环
