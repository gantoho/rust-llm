## 为什么需要分布式训练？

一个 70B 参数的模型，仅权重就需要 **140GB**（FP16），加上梯度和优化器状态：

| 组成 | 大小（FP32 优化器 + FP16 模型） |
|------|-------------------------------|
| 模型参数（FP16） | 140 GB |
| 梯度（FP16） | 140 GB |
| Adam 一阶动量（FP32） | 280 GB |
| Adam 二阶动量（FP32） | 280 GB |
| **总计** | **840 GB** |

单张 A100 80GB 显存远远不够，必须**分布到多张 GPU 上**。

## 三种并行策略

### 1. 数据并行（Data Parallelism, DP）

**每张 GPU 都有模型的完整副本**，但处理不同的数据 batch。

```
GPU 0: 完整模型 + Batch 0 → grad_0 ─┐
GPU 1: 完整模型 + Batch 1 → grad_1 ─┤→ AllReduce(平均梯度) → 各自更新
GPU 2: 完整模型 + Batch 2 → grad_2 ─┤
GPU 3: 完整模型 + Batch 3 → grad_3 ─┘
```

**AllReduce 操作**：所有 GPU 把自己的梯度汇总求平均，每个 GPU 都得到相同的平均梯度。

**优点**：实现简单，线性加速
**缺点**：每张 GPU 都要存完整模型，放不下就没法用

### 2. ZeRO（Zero Redundancy Optimizer）

DeepSpeed 提出的优化——**把优化器状态、梯度、参数分片到不同 GPU 上**：

| 阶段 | 分片内容 | 每 GPU 显存 |
|------|---------|------------|
| ZeRO-1 | 优化器状态 | 参数 + 梯度 + 优化器/N |
| ZeRO-2 | 优化器状态 + 梯度 | 参数 + (梯度 + 优化器)/N |
| ZeRO-3 | 优化器状态 + 梯度 + 参数 | (参数 + 梯度 + 优化器)/N |

```
ZeRO-3 (4 GPUs):
  GPU 0: 参数分片 0-25% + 对应的优化器状态
  GPU 1: 参数分片 25-50% + 对应的优化器状态
  GPU 2: 参数分片 50-75% + 对应的优化器状态
  GPU 3: 参数分片 75-100% + 对应的优化器状态

前向/反向时: 需要哪个参数分片就从对应 GPU 获取（AllGather）
更新时: 只更新自己负责的参数分片
```

**70B 模型在 ZeRO-3 + 8 GPU 上**：每 GPU 只需 ~105GB（接近单卡可承载）。

### 3. 模型并行（Model Parallelism）

把模型**切分到不同 GPU 上**——每张 GPU 只负责模型的一部分。

#### 张量并行（Tensor Parallelism, TP）

把**单层内的矩阵运算**切分到多张 GPU：

```
线性层 Y = X @ W，W ∈ R^{d × d}
  │
  │ 按列切分 W = [W_1 | W_2]
  │
GPU 0: Y_1 = X @ W_1  ─┐
GPU 1: Y_2 = X @ W_2  ─┤→ 拼接 Y = [Y_1 | Y_2]
```

注意力层可以按 head 切分（天然并行），FFN 可以按列/行切分。

#### 流水线并行（Pipeline Parallelism, PP）

把模型的**不同层**放在不同 GPU 上：

```
GPU 0: Layer 0-7   → 输出传给 GPU 1
GPU 1: Layer 8-15  → 输出传给 GPU 2
GPU 2: Layer 16-23 → 输出传给 GPU 3
GPU 3: Layer 24-31 → 最终输出
```

**问题**：朴素实现会导致严重的 GPU 空闲（流水线气泡）。

**解决方案——GPipe / 1F1B 调度**：

```
时间 →
GPU 0: [F1][F2][F3][F4]  [B4][B3][B2][B1]
GPU 1:     [F1][F2][F3][F4]  [B4][B3][B2][B1]
GPU 2:         [F1][F2][F3][F4]  [B4][B3][B2][B1]
GPU 3:             [F1][F2][F3][F4]  [B4][B3][B2][B1]

F = Forward, B = Backward
把一个 batch 拆成多个 micro-batch，让 GPU 尽量忙碌
```

## 3D 并行

实际大规模训练中，三种并行策略**组合使用**：

```
3D 并行 (以 256 GPU 为例):
  数据并行 × 流水线并行 × 张量并行 = 256
  例: DP=8, PP=4, TP=8

  - TP=8: 每层的矩阵运算分布在 8 张 GPU（组内高速互联 NVLink）
  - PP=4: 模型分成 4 个流水线阶段（组间用 InfiniBand）
  - DP=8: 8 组数据并行（组间 AllReduce 梯度）
```

## 通信原语

### AllReduce

所有 GPU 求和/求平均，每张 GPU 都得到结果。

```
GPU 0: grad_0 ──┐
GPU 1: grad_1 ──┤→ 平均 → 每张 GPU 都有 avg(grad)
GPU 2: grad_2 ──┤
GPU 3: grad_3 ──┘
```

实现方式：Ring AllReduce（O(2(N-1)/N × 数据量)），通信量几乎不随 GPU 数量增加。

### AllGather

每张 GPU 持有部分数据，AllGather 后每张 GPU 都有完整数据。

```
GPU 0: [参数 0-25%] ──┐
GPU 1: [参数 25-50%] ─┤→ 每张 GPU 都有 [100% 参数]
GPU 2: [参数 50-75%] ─┤
GPU 3: [参数 75-100%]─┘
```

### ReduceScatter

每张 GPU 有一份完整数据，ReduceScatter 后每张 GPU 只保留对应分片的求和结果。

```
GPU 0: [完整梯度] ──┐
GPU 1: [完整梯度] ──┤→ GPU 0 得到 [分片0的和]
GPU 2: [完整梯度] ──┤   GPU 1 得到 [分片1的和]
GPU 3: [完整梯度] ──┘   ...
```

### AllReduce = ReduceScatter + AllGather

## 梯度累积与分布式训练

分布式训练中，**有效 batch size** 会变得很大：

```
有效 batch = micro_batch × 梯度累积步数 × GPU 数量

例: micro_batch=4, 梯度累积=8, GPU=32
有效 batch = 4 × 8 × 32 = 1024
```

太大的 batch 会降低训练质量，需要相应调整学习率：

$$
\text{lr}_{\text{new}} = \text{lr}_{\text{base}} \times \frac{\text{batch}_{\text{new}}}{\text{batch}_{\text{base}}}
$$

## 混合精度与分布式

分布式训练几乎总是结合混合精度：

```
通信阶段: FP16/BF16（减少通信量 2×）
计算阶段: FP16/BF16（利用 Tensor Core 加速）
优化器更新: FP32（保持数值精度）
```

### BF16 vs FP16

| 格式 | 指数位 | 尾数位 | 范围 | 精度 |
|------|--------|--------|------|------|
| FP16 | 5 | 10 | ±65504 | 高 |
| BF16 | 8 | 7 | ±3.4e38 | 低 |

BF16 的范围与 FP32 相同，不需要损失缩放（loss scaling），训练更稳定。现代训练几乎都用 BF16。

## 通信瓶颈与优化

### 通信量估算

以 ZeRO-3 训练 70B 模型为例：

```
前向: AllGather 参数 140GB (每层一次，分摊到整个前向)
反向: AllGather 参数 140GB + ReduceScatter 梯度 140GB
总计: ~420GB 通信量 / step

用 NVLink 600GB/s: ~0.7 秒通信
用 InfiniBand 400Gb/s (~50GB/s): ~8.4 秒通信
```

### 计算-通信重叠

```
理想情况:
  [计算层 1]  [计算层 2]  [计算层 3]
  [通信层 0]  [通信层 1]  [通信层 2]  ← 通信与计算重叠
```

### 梯度压缩

在数据并行中，AllReduce 梯度时可以用低精度（FP16 甚至 INT8）减少通信量。

## 本项目的实际实现

上面的原理已全部落地为可运行代码。核心文件是 [`src/distributed.rs`](../src/distributed.rs)（25 个单测），
CLI 入口是 [`distributed`](../README.md#12-quant--distributed--align--rag--speculative--第-3338-课实验) 子命令。

### 代码结构

| 组件 | 位置 | 说明 |
|------|------|------|
| `CommLog` | `distributed.rs` | 集合通信的通信量统计：记录通信轮数和每个 rank 累计发送的元素个数，提供 `total_sent()`/`per_rank_bytes()`/`max_rank_bytes()` |
| `World` | `distributed.rs` | N 进程通信域的单进程模拟：持有所有 rank 的缓冲，提供 `all_reduce_sum`（环形两阶段）/`reduce_scatter_sum`/`all_gather`/`broadcast`/`barrier` 等集合通信原语 |
| `DataParallel` | `distributed.rs` | 数据并行控制器：封装 World，通过 allreduce 同步梯度，使多副本参数始终保持一致 |
| `ZeroStage` / `ZeroOptimizer` | `distributed.rs` | ZeRO-1/2 优化器：`One` 切优化器状态（m/v），`Two` 再切梯度（reduce-scatter 替代完整 allreduce），显存从 O(N) 降到 O(1) |
| `ColumnParallelLinear` | `distributed.rs` | 列并行线性层：输出维按列切分，前向时各 rank 只算自己的列，需要完整输出时做一次 all_gather |
| `RowParallelLinear` | `distributed.rs` | 行并行线性层：输入维按行切分，各 rank 计算部分和后 allreduce 求和，与列并行配对使用 |
| `TensorParallelMlp` | `distributed.rs` | 张量并行 MLP：组合列并行（第一层）+ 行并行（第二层），整块只通信一次 |
| `Schedule` / `Step` | `distributed.rs` | 流水线调度计划：事件表（`Forward`/`Backward` 序列）+ 显存驻留峰值分析 |
| `Pipeline` / `RunReport` | `distributed.rs` | 流水线并行执行器：按事件表依次执行前向和反向，报告各 micro-batch 输出和峰值驻留 |
| `DistConfig` / `RankCoord` / `RankPlan` | `distributed.rs` | 3D 并行配置：定义 dp/tp/pp 三个轴的切分，rank 与三维坐标的映射，每个 rank 的分工清单 |
| `flatten_grads` / `write_grads` / `flatten_params` / `write_params` | `distributed.rs` | 梯度/参数的拍平与还原工具，供集合通信和 ZeRO 分片使用 |
| `contiguous_columns` / `contiguous_ranges` / `qkv_head_columns` | `distributed.rs` | 权重切分工具：连续列/行切分 + 融合 QKV 按 head 切分（避免在 head 内部切分导致每步通信） |

### CLI 用法

```bash
# 默认配置（dp=4, tp=2, pp=2，即 16 卡模拟）
cargo run --release -- distributed

# 调整并行度
cargo run --release -- distributed --dp 8 --tp 4 --pp 2

# 调整流水线参数
cargo run --release -- distributed --micro-batches 8

# 调整训练参数
cargo run --release -- distributed --steps 80 --batch-size 4 --lr 0.01

# 调整模型规模
cargo run --release -- distributed --n-embd 64 --n-layer 4 --block-size 64

# 单机多卡（只用数据并行）
cargo run --release -- distributed --dp 8 --tp 1 --pp 1
```

> 核心内容已全部实现（`src/distributed.rs` + `distributed` 子命令），这里是进阶拓展。

4. **通信量计算**：给定模型大小和 GPU 数量，计算不同并行策略下的通信量。
