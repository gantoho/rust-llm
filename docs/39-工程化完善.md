## 2. CLI 子命令设计

### 2.1 从 4 个到 16 个子命令

| 子命令 | 功能 | 状态 |
|--------|------|------|
| `train` | 训练模型 | 增强（指标日志、早停、梯度累积） |
| `eval` | 评估模型 | 不变 |
| `generate` | 生成文本 | 增强（支持 Beam Search） |
| **`chat`** | 交互式对话 | **新增** |
| **`sft`** | 监督微调：用「提问→回答」语料把只会续写的预训练模型教会应答 | **新增** |
| **`finetune`** | LoRA 微调：冻结预训练主干，只训练挂载的低秩适配层（缺省 Q/K/V，可扩到 O 与 MLP） | **新增** |
| **`preset`** | 生成预设配置 | **新增** |
| `demo` | 端到端演示 | 不变 |

| **`scaling`** | Scaling Laws 实验：预算规划（20:1 / 参数化闭式解 / 时长电费）+ 多规模实测扫描与幂律拟合 | **新增**（第 31 课） |
| **`moe`** | MoE 稀疏专家实验：参数口径 / 负载均衡 / 端到端对照 / 容量因子与 Token Dropping | **新增**（第 32 课） |
| **`quant`** | 权重量化：RTN / Hessian 量化 / AWQ 三种 weight-only 量化（int8 / int4），含校准集与逐层误差报告 | **新增**（第 33 课） |
| **`distributed`** | 分布式训练实验：集合通信量对照 + DP / ZeRO-1/2 / TP / PP / 3D 切分报告 | **新增**（第 38 课） |
| **`align`** | 对齐实验：奖励模型排序准确率 + DPO 偏好边界 + GRPO 组内优势 + PPO 裁剪与 KL | **新增**（第 36 课） |
| **`rag`** | RAG 实验：分块不变量 + 三种向量化对照 + top-k / MMR 检索 + 提示组装 | **新增**（第 37 课） |
| **`speculative`** | 推测解码与 MTP 实验：无损性核对 + 接受率 / 加速比 + 缓存不变量 + 分布等价 + MTP 头当草稿 | **新增**（第 34/35 课） |

### 2.2 设计原则

1. **渐进式复杂度**：新手用 `demo` 验证 → `preset` 生成配置 → `train` 训练 → `generate` 生成。
   进阶用户用 `chat` 对话 → `sft` 教会应答 → `finetune` 微调。
2. **配置优先**：超参数全在 `config/config.json`。命令行只覆盖少数高频项：`generate` / `chat` 的采样参数、`sft` 的 `--sft-file/--steps/--lr/--out-dir`、`finetune` 的 `--lora-rank/--lora-alpha/--lora-targets/--resume-lora/--steps/--lr`（会覆写 `cfg.train` 对应字段）、`bench` 的 `--steps/--gen-tokens`；`train` 本身只接受 `--config` 与 `--resume`，`eval` / `chat` / `generate` 只接受 `--config` / `--ckpt` / `--tokenizer`（加各自的采样参数与 `--merge-lora`）。
3. **合理默认值**：所有参数都有默认值，最简情况只需 `cargo run -- train`。

## 3. 分词器序列化

### 3.1 为什么需要持久化

训练 BPE 分词器需要遍历整个语料统计频率，大语料（>100MB）可能耗时数十秒。
每次 eval / generate 都重新训练分词器是浪费。持久化后：
- 训练一次，保存到 `tokenizer.json`
- eval / generate / chat 直接加载，秒级完成
- 保证训练和推理用完全相同的词表

### 3.2 JSON 格式

```jsonc
// CharTokenizer
{
  "type": "char",
  "chars": ["H", "e", "l", "o", " ", "W", "r", "d"]
}

// BPETokenizer
{
  "type": "bpe",
  "merges": [[108, 111], ...],  // 合并规则（字节对）
  "vocab": [[72], [101], ...]   // token id → 字节序列
}
```

### 3.3 自动保存

训练时如果 `tokenizer_file` 未配置，会自动保存到 `{out_dir}/tokenizer.json`：

```jsonc
{
  "train": {
    "tokenizer_file": null  // null = 从语料训练并自动保存
  }
}
```

指定路径则直接加载，跳过训练：

```jsonc
{
  "train": {
    "tokenizer_file": "checkpoints/tokenizer.json"  // 直接加载
  }
}
```

### 3.4 推理时自动加载分词器（`eval` 仍要语料）

训练完成后，`eval` / `generate` / `chat` **都不再需要单独指定分词器文件**——它们会从 checkpoint 目录
自动加载 `tokenizer.json`。但要注意"不用给分词器"不等于"不用给语料"：

| 命令 | 需要分词器 | 需要语料 |
|------|-----------|---------|
| `generate` / `chat` | 自动加载 | **不需要** |
| `eval` | 自动加载 | **需要**：要算验证集 loss，仍会读配置里的 `train_file`（或 `val_file`） |

所以 `eval` 的 `--config` 必须指向语料还在的原配置；用 `train_file` 已经被删掉的配置会直接报错。

代码中通过 `load_tokenizer_for_inference` 函数实现自动查找：

```rust
// src/main.rs
fn load_tokenizer_for_inference(tcfg: &config::TrainConfig, expect_vocab: usize) -> Tokenizer {
    // 1. 用户显式配置了 tokenizer_file
    if let Some(ref path) = tcfg.tokenizer_file {
        return Tokenizer::load(path);
    }
    // 2. 自动查找训练时保存的 tokenizer.json
    let auto_path = format!("{}/tokenizer.json", tcfg.out_dir);
    if std::path::Path::new(&auto_path).exists() {
        return Tokenizer::load(&auto_path);
    }
    // 3. 都没有，从语料训练（兜底）
    let train_text = load_text(&tcfg.train_file);
    build_tokenizer(tcfg, &train_text, expect_vocab)
}
```

命令行还支持 `--tokenizer` 参数直接指定路径，优先级最高：

```
1. --tokenizer 参数（命令行显式指定）
2. config/config.json 的 tokenizer_file 字段
3. {out_dir}/tokenizer.json（训练时自动保存的，推荐）
4. 从 train_file 语料训练（兜底，不推荐）
```

这样保证了：
- 训练和推理使用完全相同的分词器（词表一致性）
- 推理时不需要原始语料文件（`eval` 除外，它要算 loss）
- checkpoint 目录可以独立复制到其他机器使用

## 4. 预设配置

### 4.1 三个预设

| 预设 | 参数量 | 架构 | 隐藏维度 | 层数 | 上下文 | 适合场景 |
|------|--------|------|----------|------|--------|----------|
| `small` | ~3.3M | 经典风格 | 256 | 4 | 128 | 学习/演示，CPU 几分钟 |
| `medium` | ~26M | LLaMA 风格 | 512 | 8 | 256 | 中等语料，推荐 GPU |
| `large` | ~79M | LLaMA 风格 | 768 | 12 | 512 | 较大语料，需要 GPU |

> 参数量口径：`词嵌入(vocab×d)` + `每层(注意力 Q/K/V/O + MLP + 归一化)` × 层数 + `ln_f`。
> 模型用 RoPE，**没有可学习的位置嵌入表**，所以不含 `block_size×d`；词表由语料训练出的分词器决定
> （`vocab_size: 0`），实际参数量会随语料略有浮动。
>
> 另外，预设**只覆盖模型结构和训练超参**，`train_file` / `out_dir` 这些沿用 `TrainConfig` 默认值
> （`data/alice.txt` 与 `checkpoints`）。仓库自带的 `config/config.json` 才被改成了中文语料 +
> `out_dir = checkpoints/zh`，所以文档里出现的 `checkpoints/zh/...` 都对应它。

### 4.2 使用方式

```bash
# 生成配置文件
cargo run --release -- preset --name medium --output config/config_medium.json

# 用生成的配置训练
cargo run --release -- train --config config/config_medium.json
```

### 4.3 架构选择

- **small** 使用经典风格（LayerNorm + GELU MLP + 标准 MHA），适合学习基础
- **medium / large** 使用 LLaMA 风格（RMSNorm + SwiGLU + GQA），与现代 LLM 对齐

## 5. 监督微调（`sft`）：把"只会续写"变成"会回答"

### 5.1 预训练和 SFT 差在哪

预训练的目标是"给定前文，预测下一个 token"，所以模型学到的本事是**续写**：你输入
`用户：今天天气怎么样？`，它会顺着往下编，甚至编出下一句"用户："。SFT 不换模型结构，
只换**数据和 loss 的算法**：

| | 预训练 `train` | 监督微调 `sft` |
|---|---|---|
| 数据 | 连续文本 | 「提问 → 回答」对话语料 |
| 加载器 | `DataLoader` | `SftLoader`（每批多带一个 loss 掩码） |
| 每个位置都算 loss？ | 是 | **否**：只有回答正文与结尾标记被监督 |
| 起点 | 随机初始化 | `--pretrained` 预训练权重（**只读**，不会被覆盖） |
| 输出目录 | `checkpoints/zh/` | `checkpoints/zh-sft/`（自动加 `-sft` 后缀） |

不在"提问"上算 loss 是关键：提问是**给模型的上下文**，不是它该学会生成的东西。
把提问也当训练目标，模型就学会了"自己提问自己回答"——这是很多简陋 SFT 实现
训出来会自问自答的直接原因。

### 5.2 对话语料格式与角色识别

语料就是普通 `.txt`，用角色标记分行（仓库示例在 `data/sft/`）：

```text
用户：今天天气怎么样？
助手：今天晴，气温 20 到 26 度，适合出门。
用户：明天呢？
助手：明天有雨，记得带伞。

A: 吃了吗
B: 吃了
```

固定标签 `用户` / `助手` / `A` / `B` 有明确含义，也可以用人名标签（`面试官：` / `陈教授：`）。
一段对话末尾的 `。。` 由程序自动补，**不用自己写**。

解析规则在 [data.rs](file:///d:/Code/Rust/llm_from_scratch/src/data.rs) 的 `parse_dialogues`：

- **标记长什么样**：行首 `<标签>：` 或 `<标签>:`，标签 1~8 个字符且全为字母数字（含汉字）。
  所以 `A:` / `用户：` / `面试官：` / `陈教授：` 都认，而 `2024年数据：……` 这类正文不会被误判成角色行。
- **谁是提问方**：`用户` / `A` 固定是提问方，`助手` / `B` 固定是回答方；人名标签（如 `陈教授`）
  没有固定含义，按**该文件里首次出现的顺序**判定——第一个出现的算提问方（对话语料里总是提问方先说）。
- **角色是文件级属性**：换一份语料，先说的人可能换成另一个人，所以每解析一个文件都要重建一次角色表。
  这也是 `load_texts` 按文件加载、而不是拼成一大份文本的原因——拼接会让后面文件里的角色弄反。
- **多行回答不会被腰斩**：某个角色行之后的所有非空行都续到当前角色上；空行只在"回答已经出现"时
  才当作一段对话的结束，否则提问与回答之间的空行会把它们拆散。
- **人名标签只在"整份文件一眼就能看出是对话语料"时才接受**：非空行里 ≥90% 是角色行、**且说话人
  恰好只有两个**时才启用。把 `data/corpus_zh/` 这类混杂目录指给 `sft_file` 时，小说旁白会把这个
  比例稀释到 90% 以下，于是正文不会被当成对话喂进来；不带角色标记的文本整体跳过。
- **`。。` 由程序自动补**，语料里不用自己写。一轮对话必须"提问与回答都非空"才会被采纳。

### 5.3 loss 掩码：监督谁、以及为什么要右移一位

对话模板由三个**纯文本**标记拼成（`src/data.rs` 顶部常量）：

```text
用户：\n<提问>\n助手：\n<回答>\n。。\n
└────── 屏蔽（不计 loss）──────┘└─ 监督 ─┘└监督┘
```

- **为什么用纯文本标记**：字节级 BPE 本就能把任意 UTF-8 字符串编码成已有 token 的序列，
  所以模板不必动词表、不必给 embedding 扩容，也就不会出现"加了 token 之后旧 checkpoint
  的 embedding 行数对不上"的兼容问题。
- **标记必须用"高频"字，光"出现过"不够**：`#` 在 4.7M 字的语料里只出现 2 次，embedding
  基本没被训过，模板一带上 `### ` 就会把模型推进 ASCII 乱码模式（实测基座模型输出
  `'何人？」621.-----2..3E8188`）；`【】` 同理不能用在标记里（也只出现 2 次）。
  **结束标记尤其不能踩这个坑**——它每段对话都要被监督，模型必须能把它生成出来。最早选的
  `（结束）` 只满足"出现过"：`（`129 次 / `结`204 次 / `束`391 次 / `）`130 次，频率全在
  0.002%~0.008%，和被判死刑的 `#`（12 次）是同一个数量级。结果模型只学会了"回答完吐一个 `（`"，
  而 `（` 之后该接什么全无先验，实测输出被 `（结公主要了。` / `（好！"结成了。` 这类括号乱码
  淹没，`（结束）` 这个完整串几乎拼不出来、停止标记形同虚设（每轮都生成到 `max_new`，这坨
  乱码还会被写进对话历史去污染下一轮）。换成 `。。` 两头都占：`。` 是语料最高频字符
  （131,594 次 / 2.79%，输出行训得最充分），而 `。。` 这个组合在 471.9 万字里只出现 **2 次**，
  不会和正文撞车。
- **`。。` 必须有**：单轮样本如果只是"提问+回答"就结束，模型没地方学"该收尾了"，
  推理时只好像预训练那样一路续写。`chat` 也把 `。。` 和 `用户：` 都设为停止标记——
  万一没学会收尾，它会顺着模板编下一轮提问。
- **右移一位**：窗口里 `y[i] = tokens[start+1+i]`，所以第 i 个位置的掩码要看**目标** token
  所在的位置 `start+1+i`，而不是输入位置 `start+i`（见 `window_mask`）。少移这一位，整批
  监督信号会整体错开一个 token——loss 照降，学到的却是"用前一个字的答案预测后一个字"，
  形式上完全说得通，极难从结果看出来。
- **样本是打包的**：所有对话首尾相接成一条 token 流，训练时按 `block_size` 随机切窗口，
  所以一个窗口可能横跨几段对话、也可能从提问中途开始；掩码照实跟随，跨段边界的位置一样屏蔽。
- **逐段编码再拼接**，而不是先拼成一个大字符串整体编码：BPE 的合并会跨边界进行，整串编码
  可能把"标记末尾"和"正文开头"并成一个 token，监督区起点就不落在 token 边界上，掩码会错位。

### 5.4 使用方式与参数收窄规则

```bash
# 从预训练权重出发做 SFT：--pretrained 只读，权重与指标都写进 checkpoints/zh-sft/
cargo run --release -- sft --config config/config.json \
    --pretrained checkpoints/zh/best.ckpt --sft-file data/sft/ --steps 800

# 训练完用带 SFT 模板的对话（--prompt-format 默认就是 sft）
cargo run --release -- chat --config config/config.json --ckpt checkpoints/zh-sft/best.ckpt
```

`cmd_sft` 会把预训练量级的超参收窄，避免直接套到几百步的 SFT 上：

| 项 | 缺省取值 | 为什么 |
|----|---------|--------|
| `--steps` | config 的 `train.steps` | — |
| `--lr` | config `max_lr` 的 **1/10** | SFT 是在已收敛的权重上继续训，用预训练步长会把它攒下的语言能力一起冲掉（实测几百步就退化成乱码）。显式传 `--lr` 时以你给的为准 |
| `min_lr` | `max_lr × 0.1` | 跟着峰值走 |
| `warmup_steps` | `min(warmup_steps, steps/10).max(1)` | 预热太长，SFT 大部分步数都耗在爬坡上 |
| `eval_every` | `min(eval_every, steps/10).max(1)` | 配置里那是给上万步预训练的值，直接用在几百步 SFT 上会把训练压成"只在最后评估一次"：`best.ckpt` 退化成 `final.ckpt`，连续不改善才触发的早停也永远等不到第二次评估 |
| `--out-dir` | `{out_dir}-sft` | **绝不能写回 `out_dir`**：会覆盖预训练攒下的 `latest.ckpt` / `best.ckpt`，SFT 效果不好就再也回不去；指标 CSV 同理（改写到 `{out_dir}-sft/sft.csv`） |

### 5.5 跑 SFT 请用不带 `gpu` 的构建

SFT 的 loss 带逐位置掩码，GPU 的**常驻输出头**路径不吃逐位置权重，整段会回落到逐算子路径。
实测（MX150）这条回落路径比纯 CPU 还慢（392 tok/s vs 780 tok/s），长跑还会崩。`cmd_sft`
检测到 `gpu` feature 时会打印这条提示——**只有预训练 `train` 适合开 GPU**。

> SFT 在整条对齐流水线里的位置（SFT → 奖励模型 → PPO / DPO）见[第 36 课](36-RLHF与对齐.md)。

## 6. 微调工作流（`finetune` = LoRA 微调）

`finetune` 加载预训练权重后**冻结全部主干**，只训练挂在各投影上的低秩适配层（LoRA）。
**挂哪里是可配的**（`--lora-targets`）：缺省 Q/K/V，可扩到 O（`c_proj`）与 MLP——实测三档分别占
1.32% / 1.75% / 3.85% 的可训练参数。结构与 rank / alpha 一起写进存档头部，推理端照头部重建，
不存在"训练挂了 MLP、推理漏挂一半"这种静默错配。
训练循环与语料跟 `sft` 完全共用（同一份 `train.sft_file`），差别只在参数集合——这样"全参 SFT vs LoRA"
才是可对比的。原理见 [第 29 课](29-LoRA低秩适配.md)。

**冻结是三处一起做实的**，缺一处就会出现"以为冻结了、其实没冻"：

| 位置 | 做法 | 不做会怎样 |
|------|------|-----------|
| 前向 | 冻结权重走 `Tensor::matmul_frozen`，反向只求 `dx` | `dW` 白算白存（4 字节/参数） |
| 优化器 | `AdamW` / `SGD` 的 `step()` 跳过冻结参数，**连带不吃权重衰减** | 衰减项与梯度无关，冻结主干会每步朝 0 缩 |
| GPU 常驻快路 | LoRA 形态下整体让路 | 那些路径直接读权重显存、绕过 `Linear::forward`，增量被**静默丢弃** |

另有一个容易踩的坑：`requires_grad` 必须是**共享标志**（本项目改成了 `Arc<AtomicBool>`，Relaxed 原子读写）。
它早先是普通 `bool`，而 `Tensor` 派生 `Clone`——在模型上冻结、优化器手里那份仍是 `true`，冻结就失效了。

### 6.1 完整流程

```
1. 从零训练基础模型
   cargo run --release -- train --config config/config.json

2. 冻结主干、只训适配层（LoRA 微调）
   cargo run --release -- finetune --pretrained checkpoints/zh/latest.ckpt \
       --lora-rank 8 --lora-alpha 8 --steps 60 --lr 5e-5

3. 用微调后的模型对话（存档目录自包含，不必再指向基座）
   cargo run --release -- chat --ckpt checkpoints/zh-lora/best.ckpt --temperature 0.3

4.（可选）接着训这套适配层，或把增量并在主干上再推理
   cargo run --release -- finetune --pretrained checkpoints/zh-lora/best.ckpt --resume-lora --steps 60
   cargo run --release -- chat --ckpt checkpoints/zh-lora/best.ckpt --merge-lora
```

### 6.2 关键参数

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| `--lr` | 1e-4 ~ 5e-5 | 微调学习率，比从零训练小 10-100 倍（`min_lr` 自动取 `lr × 0.1`） |
| `--steps` | 500-5000 | 取决于数据量，通常远少于从零训练 |
| `--lora-rank` / `--lora-alpha` | 4-64 / 通常 = rank | 适配层的秩与缩放因子；**真正生效**——决定挂多少适配参数 |
| `--lora-targets` | `q,k,v`（缺省） | 挂载位置：`q` / `k` / `v` / `o` / `mlp` / `all`；扩挂载会同步抬高参数量占比 |
| `--resume-lora` | 关 | **链式续训**：基座是 LoRA 存档时接着训存档里那套（保留旧增量），与 rank/alpha/targets 互斥 |
| `--sft-file` | 缺省用 config 的 `train.sft_file` | 对话语料，与 `sft` 共用同一份 |
| `--out-dir` | 缺省 `{out_dir}-lora` | **绝不写回 `out_dir`**，否则会覆盖预训练攒下的 `latest.ckpt` / `best.ckpt` |

推理侧的 `--merge-lora`（`eval` / `generate` / `chat` 都支持）把 `ΔW = (α/r)·AᵀBᵀ` **就地**并进主干，
省掉每层两次小矩阵乘、数值不变；它是**不可逆**的运行时操作（合并后适配器被摘除，不能再续训），
且只作用于内存副本，存档里的 A/B 不受影响。

### 6.3 参数效率（实测）

本项目 `config/config.json`（d=128、4 层，共 1,866,496 参数）跑 `--lora-rank 8`：

```
可训练参数 = 3 个投影（Q/K/V）× 2 个矩阵（A/B）× rank 8 × d 128 × 4 层 = 24,576
可训练比例 = 24,576 / 1,866,496 = 1.32%
```

挂载范围放宽后的实测值（同一模型、同一 rank）：

| `--lora-targets` | 每层对数 | 可训练参数 | 占比 |
|---|---|---|---|
| `q,k,v` | 3 | 24,576 | 1.32% |
| `q,k,v,o` | 4 | 32,768 | 1.75% |
| `all`（含 MLP） | 6 | 73,728 | 3.85% |

日志打印的是**实测值**（`trainable_parameters()` 的长度与元素数），不是按公式预估——
估错了会立刻露馅。适配层初始 B=0，因此微调起点与基座**逐位等价**（单测断言）。

## 7. 交互式对话模式

### 7.1 功能特点

- 持续输入文本，模型实时生成回复
- 自动维护对话历史（按 token 数裁剪到上下文窗口内，给本轮生成留出空间）
- 始终使用 KV Cache 加速（推理效率最高）
- 支持系统提示词（system prompt）

### 7.2 使用方式

```bash
# 基础对话
cargo run --release -- chat --config config/config.json

# 带系统提示
cargo run --release -- chat --config config/config.json --system "你是一个有帮助的助手。"

# 调整采样参数
cargo run --release -- chat --config config/config.json --temperature 0.7 --max-new 300
```

### 7.3 实现细节

- 使用 KV Cache 实现高效多轮推理（每轮只计算新 token）
- 上下文窗口 `block_size` 在「system prompt」「对话历史」「本轮生成」三者间分配，优先级从高到低：
  - **system prompt 永远保留**：它固定在序列最前面、独立于裁剪逻辑。丢掉它不只是失忆，
    还会破坏序列开头的注意力分布（attention sink）
  - **本轮生成预留 `max_new` 个 token**：生成的 token 也占用窗口。缓存是滑动窗口（第 25 课），
    生成不会提前停，但窗口只保留最近 `block_size` 个 token——预算给得不够时，最早的输入会先滑出视野
  - **对话历史拿剩下的额度**，按 **token 数**（真调 `encode` 计数，不用字节/字符估算）从最老的轮次开始丢
- 提示信息覆盖四种情况：
  - **历史被丢弃**：首次立即提示（含丢弃量），之后每 10 次汇总一次（累计丢弃量）——
    避免"持续静默失忆"
  - 单轮输入本身超窗口
  - system prompt 占满输入预算
  - `--max-new ≥ block_size`
- 上述提示统一走 `logln`（stdout + 运行日志留痕）：日志里能复盘"从第几轮开始失忆、
  累计丢了多少 token"，不用靠回忆
- 输入 `:quit` 或 `:exit` 退出

## 11. 产物目录规范化

初版把所有产物都写在仓库根目录：`config.json`、`checkpoints_zh/`、`train.log` 混在一起，跑几次实验就分不清哪个文件属于哪个实验。现在按用途分目录：

| 产物 | 目录 | 由谁决定 |
|------|------|----------|
| 配置文件 | `config/` | `--config` / `preset --output`，默认 `config/config.json` |
| 权重（checkpoint + `tokenizer.json`） | `checkpoints/` | `train.out_dir`，默认 `checkpoints` |
| 训练指标 CSV | `logs/` | `train.log_file`，默认 `logs/train.csv` |
| 运行日志 | `logs/` | 程序自动生成，名形如 `{操作}_{时间戳}.log` |

### 11.1 自动建目录（关键）

重点是**不让用户手写 `mkdir`**。`src/config.rs` 提供两个工具函数：

```rust
/// 确保目录本身存在（checkpoint 目录、日志目录等）
fn ensure_dir(dir: &str) {
    std::fs::create_dir_all(dir).unwrap_or_else(|e| panic!("创建目录 {dir} 失败: {e}"));
}

/// 写文件前确保其父目录存在：`logs/train.csv` → 自动创建 `logs/`
pub fn ensure_parent_dir(path: &str) {
    if let Some(parent) = std::path::Path::new(path).parent() {
        if !parent.as_os_str().is_empty() {
            ensure_dir(&parent.to_string_lossy());
        }
    }
}
```

调用点放在**每一个写盘出口**，而不是散落在各调用方：

| 出口 | 位置 | 覆盖的产物 |
|------|------|-----------|
| `Config::save()` | `src/config.rs` | `preset --output` 生成的配置 |
| `checkpoint::save()` | `src/checkpoint.rs` | `latest.ckpt` / `best.ckpt` / `final.ckpt` |
| `Tokenizer::save()` | `src/tokenizer.rs` | `tokenizer.json` |
| `MetricsLogger::new()` | `src/train.rs` | `logs/train.csv` |
| `runlog::start()` | `src/runlog.rs` | `logs/{操作}_{时间戳}.log` |

这样配置里写多深的路径（如 `outputs/run1/logs/train.csv`）都会自动建好目录。`ensure_parent_dir` 对 `a.txt` 这类没有目录部分的路径是空操作，不会误建目录。

### 11.2 运行日志（自动生成）

CSV 指标日志只有数字，回答不了"这次到底跑的什么命令、用的什么配置"。所以 `train` / `eval` / `generate` / `chat` / `sft` / `finetune` 六个子命令**每次运行都会自动写一份运行日志**，实现集中在 `src/runlog.rs`：

```text
logs/
├── train_2026-09-19_14-30-12-345.log
├── generate_2026-09-19_14-35-02-118.log
└── chat_2026-09-19_14-36-40-907.log
```

- **命名**：`{操作}_{年-月-日_时-分-秒-毫秒}.log`。操作名区分不同子命令，毫秒级时间戳区分同一子命令的多次运行，所以**两次运行不会互相覆盖**（Windows 文件名不允许 `:`，时分秒之间用 `-`）。
- **时间基准**：文件名时间戳、头部「开始时间」、尾部「总耗时」同源，都取 **`main()` 入口处 `runlog::mark_start()` 记下的时刻**（即命令开始执行），因此耗时**包含**参数解析、GPU 初始化、配置与模型加载等全过程，而不是只算"日志文件建好之后"那一段。
- **时间来源**：Windows 用 `GetLocalTime` 取系统本地时间；其它平台标准库没有时区 API，退化为 UTC。

每份日志分四段：

| 段落 | 内容 |
|------|------|
| 运行头部 | 操作名、开始时间（命令开始执行的时刻）、**完整命令行**（可执行文件 + 全部参数，另附一条等价的 `cargo run` 命令便于复制复现）、工作目录、版本 / debug-release / 平台、逻辑核数与 rayon 线程数、GPU 型号 |
| 完整配置 | `--config` 解析后的**全部字段**（模型超参数 + 训练参数）以 JSON 写出；`finetune` 记的是被 CLI 覆盖后的最终配置 |
| 本次运行参数 | 该操作关心的键值对：`generate` / `chat` 记 prompt、采样参数、seed、KV cache 开关，`train` / `finetune` 记语料、分词器与参数量，`sft` 记预训练权重、SFT 语料、步数/学习率来源与 prompt 模板，`eval` 记 checkpoint 步数 |
| 运行主体与结尾 | 过程输出（训练进度行、评估点、生成文本、对话轮次）+ 结束时间与总耗时（命令开始执行 → 结束的真实墙钟耗时） |

过程输出靠 `logln!` 宏写入：它和 `println!` 一样用法，但同时打控制台和日志，所以**日志内容 = 控制台看到的一切 + 头部与完整配置**。未调用 `runlog::start()` 的子命令（`preset` / `demo` / `bench`）不产生日志文件，写入接口自动退化为空操作。

> `.gitignore` 已忽略 `config/`（默认配置除外）、`checkpoints/`、`logs/` 与 `*.log`，实验产物不会进仓库。

## 12. checkpoint 文件格式：优化器状态为什么要从 JSON 文本改成二进制

初版的 checkpoint（`LLMCP1`）其实**不是纯二进制**：参数是正儿八经的 f32 数据块，但 AdamW 的一阶动量 `m`、
二阶动量 `v` 是当 JSON 文本塞在头里的（头长啥样见下）。能跑，但有两个问题：体积被文本编码撑大了 2.6 倍，
而且训练发散时会存成一个读不回来的废文件。

```text
LLMCP1 的文件布局（改动前）
魔数 "LLMCP1\n"（7 字节）
u32 小端：JSON 头长度
JSON 头 51.3 MB ← step、best_val_loss、模型配置、opt_t、opt_m（文本）、opt_v（文本）、参数元信息
参数数据块 7.4 MB ← 按参数顺序拼接的 f32 小端
```

### 12.1 体积：文本编码把优化器状态撑大了约 3.5 倍

JSON 没有二进制类型，一个 `f32` 只能写成文本，平均要 **13~14 字节**（如 `0.000123456789012345`），
而原生 f32 只要 **4 字节**。本项目 184 万参数的模型（`config/config.json`）实测：

| 内容 | 大小 | 占比 |
|------|------|------|
| 参数数据块（f32 二进制） | 7.4 MB | 12.6% |
| JSON 头（`m` / `v` 的十进制文本 + 元信息） | 51.3 MB | 87.4% |
| **`LLMCP1` 合计** | **58.6 MB** | 100% |
| **`LLMCP2`（`m` / `v` 也改成数据块）** | **22.1 MB** | 38% |

新格式 = 7.4 MB × 3（参数 / `m` / `v` 各一个数据块），**省掉 62%**。
注意 `.ckpt` 只是文件后缀、不代表内部格式：真正需要改的不是"权重没二进制"，
而是"优化器状态被当文本存了"。

### 12.2 正确性：JSON 表示不了 NaN / Infinity

JSON 规范里没有 `NaN` / `Infinity` 字面量，`serde_json` 只好把它们写成 `null`，读回时报：

```text
解析 checkpoint 头失败: invalid type: null, expected f32
```

也就是**训练一发散，存档就变成读不回来的废文件**——而这恰恰是最需要存档的时刻。二进制按位写 f32，
`NaN` / `±Inf` 原样保留。

### 12.3 现在的格式（`LLMCP2`）

```text
魔数 "LLMCP2\n"（7 字节）
u32 小端：JSON 头长度
JSON 头：step、best_val_loss、模型配置、优化器步数 opt_t、参数元信息（名字 + 形状）、LoRA 形态（`lora`，旧档可缺省）、权重 only 标记（`weights_only`，旧档缺省为 false）
参数数据块：按参数顺序拼接的 f32 小端
一阶动量 m 数据块：与参数同样的顺序与形状（权重 only 档省略）
二阶动量 v 数据块：与参数同样的顺序与形状（权重 only 档省略）
```

格式分两档：**训练档**（`save`）写三段（参数 + m + v，体积 3× 参数量）；
**权重 only 档**（`save_weights`，头部 `weights_only: true`）只写参数段（1×），
用于量化产物落盘这类"没有优化器状态可言"的场合（`quant` 子命令的落盘走这条路径）。

**为什么还留一个 JSON 头**：头里只有标量和元信息（约 2 KB），却让文件保持"自描述"——
不用反序列化任何张量就能读出 `step`、模型配置和每个参数的名字 / 形状，`eval` / `generate`
先用它构造出结构一致的模型，再按名字把参数写回去；名字或形状对不上会直接报错，而不是把错位的数据写进模型。

**为什么三段等长**：每段长度都是「参数总元素数 × 4」，所以**文件大小只由模型结构决定、与数值无关**。
权重 only 档砍掉后两段，同样的模型从 3× 参数量降到 1×。
代价是推理端也会遇到一大堆用不到的优化器状态，所以加载拆成两条路径：

| 函数 | 用途 | 行为 |
|------|------|------|
| `load_header()` | eval / generate 先建模型 | 只读魔数 + JSON 头，不碰数据块 |
| `load_params()` | 推理 | 只解参数块，**跳过** m / v（不解码就不占内存） |
| `load_with_opt()` | `--resume` 续训 | 解出参数 + m + v + `opt_t`（`step` / `best_val_loss` 在头里）；读到 `weights_only: true` 的档时 m / v 补零 |

`best_val_loss` 在头里存的是 `Option<f32>`（`None` 表示"还没产生 best"，等价于 `+∞`），
而不是直接存 `f32::INFINITY`——原因就是 11.2 说的：非有限值一旦进 JSON 就变成 `null`。

**续训到底恢复了什么**：`step`、`best_val_loss`（在头里），以及参数、`m`、`v`、`opt_t`（三个数据块）。
少任何一项都不算续训——尤其 `opt_t` 归零会让 Adam 的偏差修正 `1 - β^t` 从 `t=1` 重来，前几步更新幅度突然放大。
权重 only 档没有 m / v 可恢复，`load_with_opt` 把它们补成全零——AdamW 零状态 + 偏差修正正好等价于
"一个刚初始化的优化器"，与词表扩展时给新增行补零是同一语义，所以拿量化落盘档 `--resume` 是合法的续训起点。
但要注意**数据采样的 RNG 不在存档里**：`--resume` 后 `rng` 是从 `seed` 重新开始的，
所以续训的 loss 轨迹不会和不中断训练逐位重合。单元测试因此只断言"存档 → 读回逐位一致"，
而不是端到端轨迹一致——这才是本项目里「精确续训」的实际含义。

> **与旧存档不兼容**：`LLMCP2` 不提供 `LLMCP1` 的转换脚本（改格式只为存得更小、更稳），旧 `.ckpt` 需要重新训练。
> 相关单元测试（`src/checkpoint.rs`）：参数 / m / v / `opt_t` 逐位往返、推理路径跳过动量块、`NaN` / `Inf` 存活、
> LoRA 存档往返（头部记 rank/alpha/targets、加载端不注入适配层必须报错）、无 `lora` 字段的旧档仍可读、
> 权重 only 档往返（体积 1×、参数逐位还原、`load_with_opt` 动量补零可续训）、无 `weights_only` 字段的旧档仍按三段读。

## 13. 关键要点

- **CLI 设计**：10 个子命令覆盖训练、评估、生成、对话、监督微调、微调、预设、演示、性能基准、缩放定律实验的完整工作流
- **分词器持久化**：训练一次保存，后续直接加载，保证一致性
- **推理自动加载分词器**：4 级优先级查找，`generate` / `chat` 连语料都不需要；`eval` 仍要读配置里的语料算验证 loss
- **预设配置**：降低新手门槛，一键生成不同规模的配置文件
- **监督微调（`sft`）**：对话语料 + loss 掩码（只监督回答，提问与角色标记屏蔽，掩码右移一位）；`--pretrained` 只读、输出到 `{out_dir}-sft`，lr/warmup/eval 按步数自动收窄；跑 SFT 用不带 `gpu` 的构建
- **LoRA 微调（`finetune`）**：冻结预训练主干、只训低秩适配层（缺省 Q/K/V，实测可训练参数 1.32%；
  `--lora-targets` 可扩到 O 与 MLP，对应 1.75% / 3.85%）；
  冻结在前向（`matmul_frozen`）/ 优化器（跳过冻结参数与权重衰减）/ GPU 常驻快路（整体让路）三处一起做实，
  存档头部记录 LoRA 形态（rank / alpha / targets），加载端先注入再恢复参数
- **链式续训与推理合并**：`--resume-lora` 接着训存档里那套适配层（保留旧增量、结构照存档）；
  `--merge-lora`（`eval` / `generate` / `chat`）把 `ΔW = (α/r)·AᵀBᵀ` **就地**并进主干，数值不变、省掉两次小矩阵乘，
  但**不可逆**——合并后适配器被摘除，不能再续训
- **交互式对话**：KV Cache 加速的多轮对话，支持系统提示
- **Beam Search CLI**：通过 `--beam` 参数直接使用，与采样生成无缝切换
- **多文件加载**：支持目录路径，自动合并 .txt 文件
- **指标日志**：CSV 格式记录训练过程（默认 `logs/train.csv`），便于分析和可视化
- **运行日志**：`train` / `eval` / `generate` / `chat` / `sft` / `finetune` 每次运行自动写一份 `logs/{操作}_{时间戳}.log`，含完整命令行、完整配置与全部过程输出，文件名带毫秒时间戳不会互相覆盖
- **产物目录规范化**：配置进 `config/`、权重进 `checkpoints/`、日志进 `logs/`，所有写盘出口都会自动建目录，产物不再散落到仓库根目录
- **checkpoint 用二进制（`LLMCP2`）**：JSON 头只放标量与参数元信息，参数 / m / v 按 f32 小端写数据块；同一个模型存档从 58.6MB 降到 22.1MB，且 `NaN` / `Inf` 不再变成读不回来的 `null`
