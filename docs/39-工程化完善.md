## 2. CLI 子命令设计

### 2.1 从 4 个到 8 个子命令

| 子命令 | 功能 | 状态 |
|--------|------|------|
| `train` | 训练模型 | 增强（指标日志、早停、梯度累积） |
| `eval` | 评估模型 | 不变 |
| `generate` | 生成文本 | 增强（支持 Beam Search） |
| **`chat`** | 交互式对话 | **新增** |
| **`finetune`** | 加载预训练权重微调（当前为全参微调） | **新增** |
| **`preset`** | 生成预设配置 | **新增** |
| `demo` | 教学演示 | 不变 |
| **`bench`** | 性能基准：固定小模型跑少量训练步与短生成，输出吞吐（tok/s） | **新增** |

### 2.2 设计原则

1. **渐进式复杂度**：新手用 `demo` 验证 → `preset` 生成配置 → `train` 训练 → `generate` 生成。
   进阶用户用 `chat` 对话 → `finetune` 微调。
2. **配置优先**：超参数全在 `config/config.json`。命令行只覆盖少数高频项：`generate` / `chat` 的采样参数、`finetune` 的 `--lora-rank/--lora-alpha/--steps/--lr`（会覆写 `cfg.train` 对应字段）、`bench` 的 `--steps/--gen-tokens`；`train` 本身只接受 `--config` 与 `--resume`。
3. **合理默认值**：所有参数都有默认值，最简情况只需 `cargo run -- train`。

## 3. 分词器序列化

### 3.1 为什么需要持久化

训练 BPE 分词器需要遍历整个语料统计频率，大语料（>100MB）可能耗时数十秒。
每次 eval / generate 都重新训练分词器是浪费。持久化后：
- 训练一次，保存到 `tokenizer.json`
- eval / generate / chat 直接加载，秒级完成
- 保证训练和推理用完全相同的词表

### 3.2 JSON 格式

```jsonc
// CharTokenizer
{
  "type": "char",
  "chars": ["H", "e", "l", "o", " ", "W", "r", "d"]
}

// BPETokenizer
{
  "type": "bpe",
  "merges": [[108, 111], ...],  // 合并规则（字节对）
  "vocab": [[72], [101], ...]   // token id → 字节序列
}
```

### 3.3 自动保存

训练时如果 `tokenizer_file` 未配置，会自动保存到 `{out_dir}/tokenizer.json`：

```jsonc
{
  "train": {
    "tokenizer_file": null  // null = 从语料训练并自动保存
  }
}
```

指定路径则直接加载，跳过训练：

```jsonc
{
  "train": {
    "tokenizer_file": "checkpoints/tokenizer.json"  // 直接加载
  }
}
```

### 3.4 推理时自动加载（无需语料）

训练完成后，推理命令（`eval` / `generate` / `chat`）**不再需要语料文件**。

代码中通过 `load_tokenizer_for_inference` 函数实现自动查找：

```rust
// src/main.rs
fn load_tokenizer_for_inference(tcfg: &config::TrainConfig, expect_vocab: usize) -> Tokenizer {
    // 1. 用户显式配置了 tokenizer_file
    if let Some(ref path) = tcfg.tokenizer_file {
        return Tokenizer::load(path);
    }
    // 2. 自动查找训练时保存的 tokenizer.json
    let auto_path = format!("{}/tokenizer.json", tcfg.out_dir);
    if std::path::Path::new(&auto_path).exists() {
        return Tokenizer::load(&auto_path);
    }
    // 3. 都没有，从语料训练（兜底）
    let train_text = load_text(&tcfg.train_file);
    build_tokenizer(tcfg, &train_text, expect_vocab)
}
```

命令行还支持 `--tokenizer` 参数直接指定路径，优先级最高：

```
1. --tokenizer 参数（命令行显式指定）
2. config/config.json 的 tokenizer_file 字段
3. {out_dir}/tokenizer.json（训练时自动保存的，推荐）
4. 从 train_file 语料训练（兜底，不推荐）
```

这样保证了：
- 训练和推理使用完全相同的分词器（词表一致性）
- 推理时不需要原始语料文件
- checkpoint 目录可以独立复制到其他机器使用

## 4. 预设配置

### 4.1 三个预设

| 预设 | 参数量 | 架构 | 隐藏维度 | 层数 | 上下文 | 适合场景 |
|------|--------|------|----------|------|--------|----------|
| `small` | ~2M | GPT-2 风格 | 256 | 4 | 128 | 学习/演示，CPU 几分钟 |
| `medium` | ~15M | LLaMA 风格 | 512 | 8 | 256 | 中等语料，推荐 GPU |
| `large` | ~85M | LLaMA 风格 | 768 | 12 | 512 | 较大语料，需要 GPU |

### 4.2 使用方式

```bash
# 生成配置文件
cargo run --release -- preset --name medium --output config/config_medium.json

# 用生成的配置训练
cargo run --release -- train --config config/config_medium.json
```

### 4.3 架构选择

- **small** 使用 GPT-2 风格（LayerNorm + GELU MLP + 标准 MHA），适合学习基础
- **medium / large** 使用 LLaMA 风格（RMSNorm + SwiGLU + GQA），与现代 LLM 对齐

## 5. 微调工作流（`finetune`）

> ⚠️ **现状：LoRA 尚未接入训练循环。**
> `src/layers.rs` 的 `LoRA` / `inject_lora` 与 `--lora-rank` / `--lora-alpha` 参数都已实现，
> 但 `cmd_finetune` 只是把它们写进 `config.train.lora` 并打印一行提示，
> **不会冻结主参数、也不会注入适配层** —— 当前 `finetune` 训练的是**全部参数**。
> 可训练参数量并没有「降到 1% 以下」，LoRA 的原理与完整实现见 [第 29 课](29-LoRA低秩适配.md)。

### 5.1 完整流程

```
1. 从零训练基础模型
   cargo run --release -- train --config config/config.json

2. 加载预训练权重继续训练（当前为全参微调）
   cargo run --release -- finetune --config config/config.json \
       --pretrained checkpoints/best.ckpt --steps 1000 --lr 1e-4

3. 用微调后的模型生成
   cargo run --release -- generate --config config/config.json \
       --ckpt checkpoints/latest.ckpt --prompt "..."
```

### 5.2 关键参数

| 参数 | 推荐值 | 说明 |
|------|--------|------|
| `--lr` | 1e-4 ~ 5e-5 | 微调学习率，比从零训练小 10-100 倍（`min_lr` 自动取 `lr × 0.1`） |
| `--steps` | 500-5000 | 取决于数据量，通常远少于从零训练 |
| `--lora-rank` / `--lora-alpha` | — | **当前只做校验与打印，不生效**（见上方警告） |

### 5.3 参数效率（LoRA 的设计目标，尚未实现）

以 medium 模型（~15M 参数）为例，LoRA 接入后本应达到：

```
总参数：~15,000,000
LoRA 参数（rank=16，Q/K/V 各一个）：16 × 512 × 3 × 2 = 49,152
可训练比例：0.33%
```

注意 `cmd_finetune` 打印的那个百分比正是按这个公式**估算**出来的，
它并不代表实际可训练参数 —— 实际训练的是全部 ~15M 参数。

## 6. 交互式对话模式

### 6.1 功能特点

- 持续输入文本，模型实时生成回复
- 自动维护对话历史（按 token 数裁剪到上下文窗口内，给本轮生成留出空间）
- 始终使用 KV Cache 加速（推理效率最高）
- 支持系统提示词（system prompt）

### 6.2 使用方式

```bash
# 基础对话
cargo run --release -- chat --config config/config.json

# 带系统提示
cargo run --release -- chat --config config/config.json --system "你是一个有帮助的助手。"

# 调整采样参数
cargo run --release -- chat --config config/config.json --temperature 0.7 --max-new 300
```

### 6.3 实现细节

- 使用 KV Cache 实现高效多轮推理（每轮只计算新 token）
- 上下文窗口 `block_size` 在「system prompt」「对话历史」「本轮生成」三者间分配，优先级从高到低：
  - **system prompt 永远保留**：它固定在序列最前面、独立于裁剪逻辑。丢掉它不只是失忆，
    还会破坏序列开头的注意力分布（attention sink）
  - **本轮生成预留 `max_new` 个 token**：否则 prompt + 生成超过 `block_size` 时 KV cache 会写满，
    生成被提前截断（历史自己就超窗口时甚至只剩 1 个 token 可生成）
  - **对话历史拿剩下的额度**，按 **token 数**（真调 `encode` 计数，不用字节/字符估算）从最老的轮次开始丢
- 提示信息覆盖四种情况：
  - **历史被丢弃**：首次立即提示（含丢弃量），之后每 10 次汇总一次（累计丢弃量）——
    避免"持续静默失忆"
  - 单轮输入本身超窗口
  - system prompt 占满输入预算
  - `--max-new ≥ block_size`
- 生成层的窗口警告（`KV cache 窗口已满`）走 **stderr + 运行日志**：stdout 留给生成结果
  （可能被重定向到文件），日志留痕便于事后复盘"这次生成为什么变短了"
- 输入 `:quit` 或 `:exit` 退出

## 7. Beam Search CLI 集成

### 7.1 使用方式

```bash
# 采样生成（默认）
cargo run --release -- generate --config config/config.json --prompt "The fox" --max-new 100

# Beam Search 生成（确定性，质量更高）
cargo run --release -- generate --config config/config.json --prompt "The fox" --beam 5 --max-new 100

# 带长度惩罚
cargo run --release -- generate --config config/config.json --prompt "The fox" --beam 8 --length-penalty 0.8
```

### 7.2 采样 vs Beam Search

| | 采样 | Beam Search |
|---|------|-------------|
| 确定性 | 随机（不同 seed 不同结果） | 确定性（给定参数唯一结果） |
| 多样性 | 高 | 低 |
| 质量 | 中 | 高（全局最优） |
| 速度 | 快 | 慢（beam_size 倍） |
| 适合场景 | 创意写作、对话 | 翻译、摘要、事实性生成 |

## 9. 训练指标日志

### 9.1 启用方式

```jsonc
{
  "train": {
    "log_file": "logs/train.csv"  // 默认值；logs/ 目录不存在时自动创建。null = 不记录
  }
}
```

> `log_file` 的默认值就是 `logs/train.csv`，所以默认配置下训练**自动**产生日志，无需手动建 `logs/` 目录。

### 9.2 CSV 格式

```csv
step,lr,train_loss,val_loss,ppl,tokens_per_sec
1,0.00000600,4.142356,,,
2,0.00001200,4.121789,,,
...
250,0.00059400,2.345678,2.456789,11.67,12500
```

> 上表是示意值，假设 `train.max_lr = 6e-4`、`train.warmup_steps = 100`（`preset --name medium` 的默认值）：
> warmup 阶段 lr 从 `6e-4 / 100 = 6e-6` 起步、每步增加 `6e-6`，所以 step 1 / 2 是 `0.000006` / `0.000012`；
> step 250 已进入 cosine 衰减，lr 略低于 `max_lr`。换成别的配置时这些数值都会不同。

### 9.3 用途

- 绘制训练曲线（loss / lr / ppl 随步数变化）
- 监控训练速度（tokens_per_sec）
- 对比不同配置的训练效果
- 排查训练问题（loss 突然上升、学习率异常等）

## 10. 产物目录规范化

初版把所有产物都写在仓库根目录：`config.json`、`checkpoints_zh/`、`train.log` 混在一起，跑几次实验就分不清哪个文件属于哪个实验。现在按用途分目录：

| 产物 | 目录 | 由谁决定 |
|------|------|----------|
| 配置文件 | `config/` | `--config` / `preset --output`，默认 `config/config.json` |
| 权重（checkpoint + `tokenizer.json`） | `checkpoints/` | `train.out_dir`，默认 `checkpoints` |
| 训练指标 CSV | `logs/` | `train.log_file`，默认 `logs/train.csv` |
| 运行日志 | `logs/` | 程序自动生成，名形如 `{操作}_{时间戳}.log` |

### 10.1 自动建目录（关键）

重点是**不让用户手写 `mkdir`**。`src/config.rs` 提供两个工具函数：

```rust
/// 确保目录本身存在（checkpoint 目录、日志目录等）
pub fn ensure_dir(dir: &str) {
    std::fs::create_dir_all(dir).unwrap_or_else(|e| panic!("创建目录 {dir} 失败: {e}"));
}

/// 写文件前确保其父目录存在：`logs/train.csv` → 自动创建 `logs/`
pub fn ensure_parent_dir(path: &str) {
    if let Some(parent) = std::path::Path::new(path).parent() {
        if !parent.as_os_str().is_empty() {
            ensure_dir(&parent.to_string_lossy());
        }
    }
}
```

调用点放在**每一个写盘出口**，而不是散落在各调用方：

| 出口 | 位置 | 覆盖的产物 |
|------|------|-----------|
| `Config::save()` | `src/config.rs` | `preset --output` 生成的配置 |
| `checkpoint::save()` | `src/checkpoint.rs` | `latest.ckpt` / `best.ckpt` / `final.ckpt` |
| `Tokenizer::save()` | `src/tokenizer.rs` | `tokenizer.json` |
| `MetricsLogger::new()` | `src/train.rs` | `logs/train.csv` |
| `runlog::start()` | `src/runlog.rs` | `logs/{操作}_{时间戳}.log` |

这样配置里写多深的路径（如 `outputs/run1/logs/train.csv`）都会自动建好目录。`ensure_parent_dir` 对 `a.txt` 这类没有目录部分的路径是空操作，不会误建目录。

### 10.2 运行日志（自动生成）

CSV 指标日志只有数字，回答不了"这次到底跑的什么命令、用的什么配置"。所以 `train` / `finetune` / `eval` / `generate` / `chat` 五个子命令**每次运行都会自动写一份运行日志**，实现集中在 `src/runlog.rs`：

```text
logs/
├── train_2026-09-19_14-30-12-345.log
├── generate_2026-09-19_14-35-02-118.log
└── chat_2026-09-19_14-36-40-907.log
```

- **命名**：`{操作}_{年-月-日_时-分-秒-毫秒}.log`。操作名区分不同子命令，毫秒级时间戳区分同一子命令的多次运行，所以**两次运行不会互相覆盖**（Windows 文件名不允许 `:`，时分秒之间用 `-`）。
- **时间基准**：文件名时间戳、头部「开始时间」、尾部「总耗时」同源，都取 **`main()` 入口处 `runlog::mark_start()` 记下的时刻**（即命令开始执行），因此耗时**包含**参数解析、GPU 初始化、配置与模型加载等全过程，而不是只算"日志文件建好之后"那一段。
- **时间来源**：Windows 用 `GetLocalTime` 取系统本地时间；其它平台标准库没有时区 API，退化为 UTC。

每份日志分四段：

| 段落 | 内容 |
|------|------|
| 运行头部 | 操作名、开始时间（命令开始执行的时刻）、**完整命令行**（可执行文件 + 全部参数，另附一条等价的 `cargo run` 命令便于复制复现）、工作目录、版本 / debug-release / 平台、逻辑核数与 rayon 线程数、GPU 型号 |
| 完整配置 | `--config` 解析后的**全部字段**（模型超参数 + 训练参数）以 JSON 写出；`finetune` 记的是被 CLI 覆盖后的最终配置 |
| 本次运行参数 | 该操作关心的键值对：`generate` / `chat` 记 prompt、采样参数、seed、KV cache 开关，`train` / `finetune` 记语料、分词器与参数量，`eval` 记 checkpoint 步数 |
| 运行主体与结尾 | 过程输出（训练进度行、评估点、生成文本、对话轮次）+ 结束时间与总耗时（命令开始执行 → 结束的真实墙钟耗时） |

过程输出靠 `logln!` 宏写入：它和 `println!` 一样用法，但同时打控制台和日志，所以**日志内容 = 控制台看到的一切 + 头部与完整配置**。未调用 `runlog::start()` 的子命令（`preset` / `demo` / `bench`）不产生日志文件，写入接口自动退化为空操作。

> `.gitignore` 已忽略 `config/`（默认配置除外）、`checkpoints/`、`logs/` 与 `*.log`，实验产物不会进仓库。

## 11. checkpoint 文件格式：优化器状态为什么要从 JSON 文本改成二进制

初版的 checkpoint（`LLMCP1`）其实**不是纯二进制**：参数是正儿八经的 f32 数据块，但 AdamW 的一阶动量 `m`、
二阶动量 `v` 是当 JSON 文本塞在头里的（头长啥样见下）。能跑，但有两个问题：体积被文本编码撑大了 2.6 倍，
而且训练发散时会存成一个读不回来的废文件。

```text
LLMCP1 的文件布局（改动前）
魔数 "LLMCP1\n"（7 字节）
u32 小端：JSON 头长度
JSON 头 51.3 MB ← step、best_val_loss、模型配置、opt_t、opt_m（文本）、opt_v（文本）、参数元信息
参数数据块 7.4 MB ← 按参数顺序拼接的 f32 小端
```

### 11.1 体积：文本编码把优化器状态撑大了约 3.5 倍

JSON 没有二进制类型，一个 `f32` 只能写成文本，平均要 **13~14 字节**（如 `0.000123456789012345`），
而原生 f32 只要 **4 字节**。本项目 184 万参数的模型（`config/config.json`）实测：

| 内容 | 大小 | 占比 |
|------|------|------|
| 参数数据块（f32 二进制） | 7.4 MB | 12.6% |
| JSON 头（`m` / `v` 的十进制文本 + 元信息） | 51.3 MB | 87.4% |
| **`LLMCP1` 合计** | **58.6 MB** | 100% |
| **`LLMCP2`（`m` / `v` 也改成数据块）** | **22.1 MB** | 38% |

新格式 = 7.4 MB × 3（参数 / `m` / `v` 各一个数据块），**省掉 62%**。
注意 `.ckpt` 只是文件后缀、不代表内部格式：真正需要改的不是"权重没二进制"，
而是"优化器状态被当文本存了"。

### 11.2 正确性：JSON 表示不了 NaN / Infinity

JSON 规范里没有 `NaN` / `Infinity` 字面量，`serde_json` 只好把它们写成 `null`，读回时报：

```text
解析 checkpoint 头失败: invalid type: null, expected f32
```

也就是**训练一发散，存档就变成读不回来的废文件**——而这恰恰是最需要存档的时刻。二进制按位写 f32，
`NaN` / `±Inf` 原样保留。

### 11.3 现在的格式（`LLMCP2`）

```text
魔数 "LLMCP2\n"（7 字节）
u32 小端：JSON 头长度
JSON 头：step、best_val_loss、模型配置、优化器步数 opt_t、参数元信息（名字 + 形状）
参数数据块：按参数顺序拼接的 f32 小端
一阶动量 m 数据块：与参数同样的顺序与形状
二阶动量 v 数据块：与参数同样的顺序与形状
```

**为什么还留一个 JSON 头**：头里只有标量和元信息（约 2 KB），却让文件保持"自描述"——
不用反序列化任何张量就能读出 `step`、模型配置和每个参数的名字 / 形状，`eval` / `generate`
先用它构造出结构一致的模型，再按名字把参数写回去；名字或形状对不上会直接报错，而不是把错位的数据写进模型。

**为什么三段等长**：每段长度都是「参数总元素数 × 4」，所以**文件大小只由模型结构决定、与数值无关**。
代价是推理端也会遇到一大堆用不到的优化器状态，所以加载拆成两条路径：

| 函数 | 用途 | 行为 |
|------|------|------|
| `load_header()` | eval / generate 先建模型 | 只读魔数 + JSON 头，不碰数据块 |
| `load_params()` | 推理 | 只解参数块，**跳过** m / v（不解码就不占内存） |
| `load_with_opt()` | `--resume` 续训 | 解出参数 + m + v + `opt_t`（`step` / `best_val_loss` 在头里） |

`best_val_loss` 在头里存的是 `Option<f32>`（`None` 表示"还没产生 best"，等价于 `+∞`），
而不是直接存 `f32::INFINITY`——原因就是 11.2 说的：非有限值一旦进 JSON 就变成 `null`。

**续训到底恢复了什么**：`step`、`best_val_loss`（在头里），以及参数、`m`、`v`、`opt_t`（三个数据块）。
少任何一项都不算续训——尤其 `opt_t` 归零会让 Adam 的偏差修正 `1 - β^t` 从 `t=1` 重来，前几步更新幅度突然放大。
但要注意**数据采样的 RNG 不在存档里**：`--resume` 后 `rng` 是从 `seed` 重新开始的，
所以续训的 loss 轨迹不会和不中断训练逐位重合。单元测试因此只断言"存档 → 读回逐位一致"，
而不是端到端轨迹一致——这才是本项目里「精确续训」的实际含义。

> **与旧存档不兼容**：`LLMCP2` 不提供 `LLMCP1` 的转换脚本（改格式只为存得更小、更稳），旧 `.ckpt` 需要重新训练。
> 相关单元测试（`src/checkpoint.rs`）：参数 / m / v / `opt_t` 逐位往返、推理路径跳过动量块、`NaN` / `Inf` 存活。

## 12. 关键要点

- **CLI 设计**：8 个子命令覆盖训练、评估、生成、对话、微调、预设、演示、性能基准的完整工作流
- **分词器持久化**：训练一次保存，后续直接加载，保证一致性
- **推理自动加载分词器**：4 级优先级查找，推理时无需语料文件
- **预设配置**：降低新手门槛，一键生成不同规模的配置文件
- **微调（`finetune`）**：加载预训练权重继续训练；**当前是全参微调**，LoRA 的 `rank/alpha` 参数只做校验与打印，尚未冻结主参数 / 注入适配层
- **交互式对话**：KV Cache 加速的多轮对话，支持系统提示
- **Beam Search CLI**：通过 `--beam` 参数直接使用，与采样生成无缝切换
- **多文件加载**：支持目录路径，自动合并 .txt 文件
- **指标日志**：CSV 格式记录训练过程（默认 `logs/train.csv`），便于分析和可视化
- **运行日志**：`train` / `finetune` / `eval` / `generate` / `chat` 每次运行自动写一份 `logs/{操作}_{时间戳}.log`，含完整命令行、完整配置与全部过程输出，文件名带毫秒时间戳不会互相覆盖
- **产物目录规范化**：配置进 `config/`、权重进 `checkpoints/`、日志进 `logs/`，所有写盘出口都会自动建目录，产物不再散落到仓库根目录
- **checkpoint 用二进制（`LLMCP2`）**：JSON 头只放标量与参数元信息，参数 / m / v 按 f32 小端写数据块；同一个模型存档从 58.6MB 降到 22.1MB，且 `NaN` / `Inf` 不再变成读不回来的 `null`
